# /epic-flow — アウターループ

仕組みの詳細は `docs/04_ループエンジニアリング.md` 2〜3 章。

エピック: **$ARGUMENTS**

エピック = タスクが複数ある GitHub issue 1 つ。タスクの正は issue 本文のチェックリスト（`STATE.md` は issue #4 で廃止。P0〜P5 の記録は `.claude/state/archive/`）。ブランチは `issue/<番号>`。

## 手順

### 1. 計画（planner）
- issue 本文にすでに承認済みのタスク表（チェックリスト）があれば、1・2 を飛ばして 3 へ
1. `/plan <番号>` と同じ手順で planner に分解させ、リードが issue 本文に書く
2. planner が質問を返したら、**分解を進めずに人へ質問する**

### 2. 人の承認（チェックポイント 1）
- タスク表を要約して人に見せ、承認を待つ。**承認前に実装を始めない。リードが代行しない**（第2弾ではここを省いてしまった）
- 承認後、issue 本文に「（日付 人が承認）」と書き、`git switch -c issue/<番号>`（すでにその worktree / ブランチにいればそのまま）

### 3. タスクの実行（issue-flow の繰り返し）
- 依存関係の順に、タスクごとに `/issue-flow <番号> <タスクID>` を実行する。issue 本文でチェック済みのタスクは飛ばす（途中から再開できる）
- 並列にしてよいのは、docs/01 の 10.2（api の A / B / C）と 10.3（web の WA / WB / WC）だけ。**同時に実装 3 体・レビュー 4 体まで**。レビューが 4 体を超えるときは担当ごとに順番に回す
- 基盤（10.1）と非同期（10.4）は直列
- 並列中、リード（あなた）は **全担当が終わるまで終了しない**（終了すると Stop フックが途中状態の全テストを回して赤になる）
- タスクが人の判断待ちになったら、issue に `requires-human` ラベルを付けて理由をコメントし、他の独立タスクは続けつつ人に報告する

### 4. 統合
- issue 本文のタスクが全部チェック済みになったら `/verify full` を実行する
- 赤ならその時点で Stop フックの検証ループが働く。緑になるまで直す（`build-error-resolver`）

### 5. 人の最終確認（チェックポイント 2）
- push して PR を作る（本文に `Closes #<番号>`、タスク一覧、`make verify` の結果、差し戻し回数）。次を人に提示する
  - PR の URL、`make verify` の結果、`loop-log.md` の差し戻し回数
  - `myteam-acceptance` の手動確認手順のうち、このエピックで確認できるようになった項目
  - 人の作業が必要なこと（フェーズ移行、`.env` の反映、マイグレーションのロック）
- **`main` へのマージは人が行う**（マージで issue が閉じる）。フェーズを変えるときは人が `.claude/.phase` を書き換える

## ハードストップ
- planner の質問が 2 往復しても解消しない → 止めて人に判断を仰ぐ
- 同一タスクが issue-flow で 2 回人の判断待ちになる → エピック全体を一時停止（`requires-human` ラベル）
