# /issue-flow — インナーループ（タスク 1 件）

対象: **$ARGUMENTS**

**工程は必ず直列に進める。** 前の工程のサブエージェントが終わってから次を起動する。並列にしてよいのは手順 3 の 3 レビュアーだけ（tester と implementer を同時に走らせると、同じテストファイルを編集して手戻りが出る）。

## 手順

### 0. 準備
- `gh issue view <番号>` で対象タスク（担当・所有ファイル・完了条件）を読む。完了条件がなければ着手せず `/plan <番号>` に戻す
- 担当が api か web かを確定する。両方にまたがるタスクは 2 つに分ける
- **工程ごとの状態は書かない**（進行中・レビュー中を issue に書き込まない。いま何をしているかはリードの会話とブランチで分かる）
- ブランチが `issue/<番号>` でなければ作る（epic-flow の中ならすでにある）

### 1. 実装（implementer-api または implementer-web）
- タスク行・所有ファイル・完了条件・`docs/01` の該当章を渡す
- api: `tdd-workflow` に従い RED→GREEN→REFACTOR
- web: Next 16 の同梱ドキュメントを読んでから、スキーマ → ページ → Action → フォームの順
- 終了時に SubagentStop フックが変更ファイルの `php -l` + Pint、または ESLint を検査する
- 報告に「所有外ファイルの変更が必要」「API の形が契約と違う」とあれば、リードが判断する（軽微なら自分で行い、契約に関わるならリードが `docs/01` の変更案を作って人に相談する）

### 2. テスト補強（tester）— 手順 1 が終わってから
- api: F-xx の受け入れ条件と実装ファイルを渡し、条件 ↔ テストの対応表と不足テストの追加をさせる
- web: zod スキーマと docs/01 の API 契約の突き合わせ表を作らせる
- tester が「実装の不具合の疑い」を報告したら手順 1 に戻す（これも周回に数える）

### 3. 多軸レビュー（並列）— 手順 2 が終わってから
- `spec-reviewer`、`code-reviewer`、`security-reviewer` を **同時に** 起動する（読み取り専用）
- テーブル・集計・トランザクションに触れたタスクは `database-reviewer` も加える（計 4 体）
- 結果を `重大` / `推奨` / `任意` で統合する

### 4. 判定と差し戻し — 手順 3 が全員終わってから
- `重大` が 1 つでもあれば implementer に戻す（指摘表を渡す）。戻すのは **最大 2 周**。戻した後は手順 2 → 3 をもう一度通す
- 2 周しても `重大` が残る → issue に `requires-human` ラベルを付け、残った指摘をコメントして止まり、人に報告する
- `推奨` は implementer に渡して直せるものは直す。`任意` は PR の説明に残す

### 5. 完了
- api: `make api-test FILTER=<担当のテストクラス>` と `make api-pint-test` が緑
- web: `make web-typecheck` と `make web-lint` が緑
- issue 本文の該当タスクにチェックを付ける（`gh issue view <番号> --json body -q .body` → `- [ ] **ID**` を `- [x] **ID**` に → `gh issue edit <番号> --body-file -`）。**issue を更新するのはこの 1 回だけ**。レビュー周回数はコミットメッセージの本文に書く。web のタスクの手動確認は PR の説明に「手動確認: 未」と書き、人が確認する
- 小さな issue そのものがタスクなら、チェックは付けずに `/pr-create <番号>` で PR を作る。マージは人が行う（epic-flow の中なら PR は epic-flow の最後に 1 つだけ）
- 差し戻しがあり、次から防げる教訓があれば、効かせたい場所（`CLAUDE.md`・`.claude/rules/`・スキル）に同じ PR で書き足す
- `git add` した上で日本語のコミットメッセージでコミット（`feat(api): F-05 募集の作成・編集` の形式）

## 注意
- 各ステップの判定は **検証結果とレビュー表** で行う。サブエージェントの「できました」は判定材料にしない（機械的な成功判定）
- この後リードが終了しようとすると Stop フックが全テストを回す。並列で他タスクが進行中なら、リードは終了せず次のタスクへ進む
