# /issue-flow — インナーループ（タスク 1 件）

`.claude/contexts/dev.md` を先に読むこと。仕組みの詳細は `docs/04_ループエンジニアリング.md` 3 章。

対象: **$ARGUMENTS**

**工程は必ず直列に進める。** 前の工程のサブエージェントが終わってから次を起動する。並列にしてよいのは手順 3 の 3 レビュアーだけ（第2弾で tester と implementer を同時に走らせ、同じテストファイルを編集して手戻りが出た）。

## 手順

### 0. 準備
- `.claude/state/STATE.md` から対象タスクの行（担当・所有ファイル・完了条件）を読む。表にない場合は 1 行追加してから始める
- 担当が api か web かを確定する。両方にまたがるタスクは 2 つに分ける
- 状態を `進行中` にする

### 1. 実装（implementer-api または implementer-web）
- タスク行・所有ファイル・完了条件・`docs/01` の該当章を渡す
- api: `tdd-workflow` に従い RED→GREEN→REFACTOR
- web: Next 16 の同梱ドキュメントを読んでから、スキーマ → ページ → Action → フォームの順
- 終了時に SubagentStop フックが変更ファイルの `php -l` + Pint、または ESLint を検査する
- 報告に「所有外ファイルの変更が必要」「API の形が契約と違う」とあれば、リードが判断する（軽微なら自分で行い、契約に関わるなら `architect` と人へ）

### 2. テスト補強（tester）— 手順 1 が終わってから
- api: F-xx の受け入れ条件と実装ファイルを渡し、条件 ↔ テストの対応表と不足テストの追加をさせる
- web: zod スキーマと docs/01 の 6 章の突き合わせ表を作らせる
- tester が「実装の不具合の疑い」を報告したら手順 1 に戻す（これも周回に数える）

### 3. 多軸レビュー（並列）— 手順 2 が終わってから
- `spec-reviewer`、`code-reviewer`、`security-reviewer` を **同時に** 起動する（読み取り専用）
- テーブル・集計・トランザクションに触れたタスクは `database-reviewer` も加える（計 4 体）
- 結果を `重大` / `推奨` / `任意` で統合する

### 4. 判定と差し戻し — 手順 3 が全員終わってから
- `重大` が 1 つでもあれば implementer に戻す（指摘表を渡す）。戻すのは **最大 2 周**。戻した後は手順 2 → 3 をもう一度通す
- 2 周しても `重大` が残る → `STATE.md` を `requires-human` にして止まり、残った指摘を人に報告する
- `推奨` は implementer に渡して直せるものは直す。`任意` は `learnings.md` 行きの候補にする

### 5. 完了
- api: `make api-test FILTER=<担当のテストクラス>` と `make api-pint-test` が緑
- web: `make web-typecheck` と `make web-lint` が緑
- `STATE.md` の状態を `完了`、備考に「レビュー N 周」を書く。web のタスクは「手動確認: 未」と書き、人が確認したら「済」にする
- 差し戻しがあった場合は `/learn` で教訓を 1 行残す
- `git add` した上で日本語のコミットメッセージでコミット（`feat(api): F-05 募集の作成・編集` の形式）

## 注意
- 各ステップの判定は **検証結果とレビュー表** で行う。サブエージェントの「できました」は判定材料にしない（機械的な成功判定）
- この後リードが終了しようとすると Stop フックが全テストを回す。並列で他タスクが進行中なら、リードは終了せず次のタスクへ進む
