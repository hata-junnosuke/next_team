# myteam 業務ルール（要件の機能要件・設計上の論点の実装上の決定）

契約としての書き方（クラス名・引数）は `docs/01_技術仕様_next.md` のドメインが正。ここは「なぜそうか」と判断に迷ったときの基準。

## 応募の状態遷移（F-14）
```
応募中(applied) → 確定(confirmed) / 却下(rejected)
確定(confirmed) → キャンセル(cancelled)
却下・キャンセル → （終端。再承認不可）
```
- 遷移表は `App\Enums\ApplicationStatus::canTransitionTo()` の **1 箇所**
- `status` を変える唯一の入口は `Application::transitionTo()`。呼ぶのはサービスだけ
- `#[Fillable]` に `status` を入れない。モデルの `$attributes` で既定値 `applied` を持つ

## 定員（F-11）
- 承認は `DB::transaction` の中で確定数を数える。`確定数 >= capacity` なら `DomainException('定員に達しているため承認できません。')`
- SQLite は `transaction_mode=IMMEDIATE` なので、同時に 2 つ承認が来ても後の方は先のコミットを待つ
- キャンセルで定員が 1 枠空く。却下は定員に影響しない

## 時給・交通費の固定（要件の設計上の論点）
- 確定時に `confirmed_hourly_wage` / `confirmed_transport_allowance` に募集の値をコピーする。報酬計算はこの値だけを見る。募集を後から編集しても確定済みの報酬は変わらない

## キャンセル（F-13）
- 確定済みのみ対象。理由区分（企業都合 / ワーカー都合）が必須。`cancelled_at` を記録

## 募集（F-05〜F-08）
- 締切（closed）= 新規応募の受付停止。**締切後も応募中の応募は承認できる**
- 中止（cancelled）= 確定済みは「企業都合キャンセル」に、応募中は「却下」に自動遷移。中止後は編集できない
- 募集中（open）でない募集には応募できない
- 募集人数は確定数より少なく編集できない
- 複製は「同条件で別日・状態は募集中・応募は引き継がない」
- 時給は `config('myteam.min_wage')` 以上

## 応募の代行入力（F-09）
- 無効ワーカーは選択肢に出さない（`applicable-workers`）、選ばれても拒否。同一募集への二重応募は拒否（DB の UNIQUE でも守る）

## ワーカー（F-02、F-03）
- **メールは必須**（通知の宛先）。電話は任意
- 無効にしても既存の応募・確定は影響を受けない。確定済みの無効ワーカーにも通知は送る（契約は成立しているため）

## 削除しない（要件の非機能要件）
- 物理削除は「募集に使われていない拠点」だけ。ワーカーは無効化、募集は中止、応募はキャンセル

## 勤怠・報酬（F-15、F-16）
- 確定済みの応募にだけ入力できる
- 労働分 = 退勤 − 出勤 − 休憩（分）。休憩は労働時間を超えない
- 賃金 = `intdiv(労働分 × 時給 + 59, 60)`（円未満切り上げ。浮動小数を使わない）。合計 = 賃金 + 交通費
- 例: 9:00-17:00 休憩 60 分 時給 1,300 円 交通費 500 円 → 420 分 → 9,100 + 500 = **9,600 円**
- 深夜跨ぎ: 入力は `HH:MM`。退勤 ≤ 出勤なら **翌日扱い**、同時刻はエラー。日付は募集の勤務日から組み立てる
- 勤怠保存時に `worked_minutes` / `wage_pay` / `total_pay` を確定して保存する。月次集計はこれを `SUM` する

## 月次集計（F-17）
- 対象は「募集の勤務日が対象月に入る」勤怠。深夜跨ぎで翌月に退勤しても勤務日の月に入る
- 範囲は半開区間（`>= 月初 AND < 翌月初`）
- ワーカー別・拠点別の報酬合計と勤務回数。キャンセルされた応募の勤怠は含めない

## テナント分離（要件の利用者と権限）
- 企業は `CurrentCompany::id()` で決まる。未設定なら例外（黙って全件を返さない）
- 他社のデータは 404
